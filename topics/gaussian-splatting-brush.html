How & Why

3D Gaussian Splatting (3DGS) represents a scene as millions of tiny colored 3D Gaussians. Given a set of posed photos, the Gaussians are optimized until they reproduce the images, giving a radiance field that renders novel viewpoints in real time.

The usual toolchain (CUDA toolkit, Python, custom compilation) is a barrier. This project uses Brush, a WebGPU-based engine: no CUDA, no Python, no compile step. The full pipeline (posed images to Gaussian training to an exported .ply to real-time viewing) runs on a laptop GPU (RTX 3500 Ada) using only ~3.6 GB of VRAM.

Takeaway: What Transfers When Implementing 3DGS

3DGS gets faster mainly by doing less work on fewer primitives, not by micro-optimizing kernels. Two ideas carry over to any stack (gsplat, Nerfstudio, atlas-gsplat), and the first one dominates everything else.

1

Fix the splat budget and place with MCMC

The single highest-impact lever.

Vanilla 3DGS grows the model by adaptive densification: wherever image error is high it clones and splits Gaussians, with no ceiling. The count balloons to millions, and a large share are "dead" splats sitting in already-solved regions or empty space. Every extra Gaussian is paid for at every step, in sorting, rasterization, and the backward pass.

The fix is to set a hard cap and drive placement with MCMC (Markov-Chain Monte Carlo). Instead of cloning forever, MCMC treats splats as movable samples: it removes low-opacity, low-contribution splats and respawns them where error is highest. The budget is always spent where it matters, so you reach quality comparable to gsplat/inria with roughly half the primitives, lower VRAM, and a faster pipeline end to end.

Unbounded densification~2-4M splats, many wasted (red)
→
Fixed budget + MCMC~half the splats, all on the surface

How to use it: in Brush it is the default via --max-splats; in gsplat it is MCMCStrategy with cap_max. This single choice dominates the speed / quality / memory trade-off.

2

Cull tighter and fuse the backward pass

Cut wasted work once the budget is fixed.

Two smaller wins, both about memory traffic (the real bottleneck). First, each Gaussian is normally assigned to screen tiles with a loose axis-aligned bounding box, so it touches tiles it never actually covers and blends them for nothing. Fitting the splat to the tiles it truly overlaps removes that wasted blending.

Second, the backward pass usually writes gradients out to global memory and the optimizer reads them back. Fusing gradient computation with the optimizer step keeps those values in registers and shared memory, avoiding the round trip. See Speedy-Splat and Faster-GS.

Training Command

Reproduce the run with the prebuilt brush_app.exe (no installation) on the truck dataset:

Train (PowerShell)

.\brush_app.exe "data\tandt\truck" `
  --total-steps 30000 --max-splats 3000000 --max-resolution 1600 `
  --eval-split-every 8 --eval-every 5000 --eval-save-to-disk `
  --export-path "output\truck" --export-name "truck_{iter}.ply" --export-every 10000

The key flags:

  • --max-splats 3000000 is the budget cap from Takeaway 1, the main quality-versus-VRAM lever. The run settled at 1.63M, well under the cap.
  • --eval-split-every 8 holds out every 8th image for evaluation, so the renders shown above are on views never used for training.
  • --total-steps, --max-resolution, and the --export-* flags control training length, input resolution, and when the .ply is written to disk.

View the exported model locally with .\brush_app.exe "output\truck\truck_30000.ply".
